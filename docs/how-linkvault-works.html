How LinkVault works

LinkVault reads a chat export, finds every link in it, and turns them into a list you can search as you type, even at 100,000 links. All of it runs in your browser and nothing is uploaded. This page follows one link from the text to the screen, and shows why each step stays fast.

lib/workers/

Two threads and a database

A browser page has one main thread. It draws the screen and answers clicks and key presses. If it spends a second parsing a chat, the page freezes for that second. So LinkVault does all heavy work in a Web Worker, a second thread with no access to the screen. The two talk by sending each other messages.

Everything is stored in the browser's own database, IndexedDB, through a library called Dexie. The worker writes the links there and reads them back. The page reads only the small tables itself: sources, stars and settings. That is why a star shows the moment you press s.

lib/extract/

Finding the links

An import goes through the same steps every time. The first three read the whole text. The rest run only on the bits of text that look like links, which are a tiny share of it.

Splitting a chat into messages

LinkVault first works out what kind of text it has. If at least 60% of the first 50 lines look like WhatsApp headers, such as 14/03/2026, 21:03 - Sam:, it reads the file as a WhatsApp chat. Between 20% and 60% it asks you. Otherwise each line is its own message.

A line without a header belongs to the message above it, so a message can span several lines. Whether dates are day-first or month-first is settled by reading every date in the file first: a first number above 12 can only be a day. Each message gets a fingerprint made from its minute, sender and text. A newer export of the same chat gives the same fingerprints, so updating a chat adds only the new links.

One regular expression

Each message's text goes through one regular expression (lib/extract/url/find.ts). It matches anything that starts like a link: https:// or http://, www., or a bare domain like github.com/vercel/next.js. A match runs until it reaches a character a link can't contain: a space, a quote, an angle bracket, an emoji, an invisible formatting character, or Chinese and Japanese punctuation.

The expression is built once. The browser's regex engine is native code and walks the text in a single pass, so the scan itself costs little. Most of the work after it happens on a handful of candidates per message.

One link, step by step

Here is one line from a chat, and what happens to the link in it.

14/03/2026, 21:03 - Sam: the tram video I mentioned (https://www.youtube.com/watch?v=abc123&si=XYZ).

  1. Find
    the tram video I mentioned (https://www.youtube.com/watch?v=abc123&si=XYZ).

    The match runs to the end of the line, since brackets and full stops can appear inside real links.

  2. Trim
    https://www.youtube.com/watch?v=abc123&si=XYZ).

    The full stop ends the sentence, and the bracket has no partner inside the link, so both go.

  3. Check

    The browser's URL parser accepts it, it is https, and the host has a dot. Code pasted into a chat, like https://api.example.com/users/${id}, is turned away here.

  4. Clean
    https://www.youtube.com/watch?v=abc123&si=XYZ

    si is YouTube's share tracking. This cleaned URL is the one you see, open and export. The original is kept too.

  5. Key
    https://www.youtube.com/watch?v=abc123

    The key decides what counts as a duplicate. youtu.be/abc123 and m.youtube.com/watch?v=abc123 get the same key, so they count as one link.

  6. Describe

    Site youtube.com, kind video, sent by Sam on 14 March 2026 at 21:03. The message around the link is kept as its context, up to 200 characters.

Bare domains

Links without https:// are the risky ones, because plenty of ordinary text looks like name.ending. A bare match counts only if its ending is on the public suffix list, the registry of real domain endings that browsers use. Endings that double as file types or code words, like .md, .py or .id, also need a path.

In the textResultWhy
github.com/vercel/next.jskept.com is a real ending

allegro.pl/oferta/1kept.pl is also a file type, but the path settles it

The same list decides which site a link is grouped under. m.youtube.com and news.bbc.co.uk group as youtube.com and bbc.co.uk, while alice.github.io stays a site of its own.

Saving

The links are written in one database transaction, a thousand at a time, with progress shown. If you cancel, close the tab or run out of disk, nothing is half-saved. The original text is kept, compressed, so a source can be read again when the parser improves.

lib/library/rows.ts

Handing the library to the page

A stored link is a big record: the message, its position, the URL as found, and more. The list needs only a little of it. So the worker reads every link, 10,000 at a time, and builds a compact copy called the lean rows.

The rows are stored by column. Each kind of text, such as all the titles, is one long string with the rows joined by a \0 character, plus an array of where each row starts. Numbers such as dates and kinds go into typed arrays, which are plain blocks of binary numbers. Values that repeat, like site names, are stored once, and each row keeps a small number that points at its value.

This matters when the rows cross from the worker to the page. Sending 50,000 objects means copying them one at a time. A typed array is different: its memory can be handed over to the page, so nothing is copied at all.

Each row also carries its search text, made ahead of time: the URL, title, message text, sender and the site's other names, lowercased and with accents removed. That is why belem finds Belém, and x.com finds links saved as twitter.com.

lib/query/view.ts

Search and filters

Search runs on the page at every keystroke, over the lean rows. For each word you type, it calls indexOf on the one long search string. indexOf is the browser's built-in text search, and it is very fast. On a hit, the offsets say which row the hit is in. The search then jumps to the start of the next row, because one hit per row is enough.

The filters and the counts beside them come from a single loop over every row, which checks each row against all the filters at once. A row that fails exactly one filter still counts toward that filter's options. So each number tells you how many links you would get if you also picked that value.

Sorting is cheap because the rows arrive newest first. Oldest first is the same list read backwards. Sorting by site or by import drops each row into a numbered bucket, a counting sort that takes one pass. Collapsing duplicates is counting too, because copies of a link share one number.

The search box shows each letter as you type it. React's useDeferredValue lets the list catch up a frame later, so typing never waits for the list.

components/library/LinkList.tsx

Drawing 98,000 rows

The list is virtualized, so only the rows you can see exist in the page. Every row is exactly 50 px tall. A list of 98,000 links is an empty box 4.9 million pixels tall, and the scrollbar behaves as if every row were there.

When you scroll, working out which rows are in view takes one division, because no row ever has to be measured. Those rows are drawn, plus 8 above and 8 below so that fast scrolling doesn't show gaps. Each row is moved into place with a CSS transform.

Each row reads its own data straight from the columns by number, and only those rows format anything for display. The React Compiler keeps rows that stay on screen from being redrawn as you scroll. For the keyboard, only the current row is in the Tab order; j and k move between rows and scroll as needed.

Known limits

  • Saving is the slowest step. IndexedDB charges for every record, about 22,000 links a second. Packing links into blocks would save faster, but search, stars and re-extract are built on one record per link, so faster saving is left for later.
  • The list has a height ceiling. Browsers cap how tall an element can be. At 50 px a row, the list can reach about 360,000 links in Firefox and 670,000 in Chrome and Safari. Past that, rows would need scaled positions.
  • Search is a straight scan. At 100,000 links it stays well inside its budget. Beyond that, the PRD plans a proper search index (MiniSearch).
